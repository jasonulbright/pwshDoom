# Existing implementations

Initial survey: 2026-09-10. The 2026-10-20 refresh checked current repository pages and README claims for architecture, ownership, and features; older local source inspections retain the scope noted in their rows. This is a comparison of documented architecture and scope, not an equivalent benchmark or independent campaign certification. It is not an exhaustive proof that no other port exists. Author-described features are not independently reproduced unless explicitly stated.

Other compiled terminal presentations include [jserv/kitty-doom](https://github.com/jserv/kitty-doom), which documents a C/PureDOOM engine and Kitty graphics protocol. Its README was reviewed 2026-10-20; it is not built or benchmarked here. The projects above show that “Doom in a terminal” has several real implementations; they are prior art for display experiments, not evidence about PowerShell engine performance.

## Assessment

This project occupies a narrower intersection: Doom gameplay, rasterization, terminal encoding and audio synthesis/mixing algorithms written in PowerShell, with a Windows Terminal host and user-supplied game data. The single-file PowerShell project now documents a broad playable subset, while listing moving sectors, walk-over triggers and sound as unfinished; its current support and performance remain author-described. Other terminal offerings use compiled engines, browser/WASM or Kitty graphics rather than PowerShell algorithms with Windows Terminal output. This makes pwshDoom a distinctive fit for the stated language-and-host constraint, not a demonstrated performance or compatibility winner. We have not run equivalent campaign, fidelity, audio or pacing trials against these alternatives. The survey must not be used to claim “best,” “first,” or full-WAD support. Check licenses before adopting code.

**Measured follow-up:** the first batch evaluated nick0451's BSP walls/flats/sky renderer from commit `6b0072973cd08fb83edc521e834e4070cda4b0a5`, using a separately stored source file and the user's Steam Doom IWAD. The low-resolution combined renderer/encoder/write loop reached 75–76 completed writes/second with the study's ANSI encoder in the corrected UTF-8 runs. This excludes gameplay and displayed-frame verification. See [full findings](findings-2026-09-10.md); it is not a reproduced upstream full-game performance claim.

## Assets

Users supply commercial IWADs. The engine source release does not release commercial graphics, music, or maps. [Freedoom explains the separation](https://freedoom.github.io/about.html) and provides independent replacement content. [Chocolate Doom documents obtaining the shareware IWAD](https://www.chocolate-doom.org/wiki/index.php/FAQ#Why_does_the_game_crash_just_after_the_title_screen_appears?). Availability of a WAD does not prove a particular port supports its full feature set.
