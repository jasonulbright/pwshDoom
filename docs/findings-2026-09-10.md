# First feasibility findings — 2026-09-10

PowerShell Doom already exists. A worthwhile study is how well existing PowerShell rendering and gameplay can work with modern terminal output. This first batch demonstrates real WAD-based scene rendering at useful low-resolution update rates, and identifies substantial encoding costs. It does not establish a complete playable port or monitor-visible FPS.

## Existing work

[ManagedDoomPowershell](https://github.com/oleyska/ManagedDoomPowershell) translates a substantial Doom engine into PowerShell and presents in a graphical window. [nick0451/doom-powershell](https://github.com/nick0451/doom-powershell) already implements WAD-based geometry, terminal output, and simplified gameplay in PowerShell. Its missing sector actions and audio matter for a faithful port. The [comparison](existing-implementations.md) distinguishes these from C/C# engines merely launched by PowerShell.

This study tested the latter project's geometry renderer through a small adapter. Its source stays in ignored `local/`; the inspected repository had no explicit license. No existing project's campaign completion was independently tested.

## Machine and method

Measured on a Core Ultra 7 265K, 32 GiB DDR5-7200, RTX 4070 Ti SUPER, Samsung 9100 PRO 2TB, and 3440x1440/165 Hz desktop. Windows 11 Pro build 26200, Windows Terminal 1.24.11911.0, PowerShell 7.6.5. The PowerShell executable was the bundled task runtime; the normal Terminal default profile was not changed. See [environment.json](../results/environment.json).

A separate Terminal profile requested Cascadia Mono 7pt, aliased text, opaque background, zero padding, and no acrylic. The process reported 589x128 cells. ANSI uses two logical pixels per cell, whereas Sixel uses raster pixels; equal logical resolution did **not** imply equal physical image size. The tools did not expose the Terminal window for visual inspection, so profile appearance and displayed image correctness were not independently confirmed.

All algorithms added by this study use PowerShell and standard .NET APIs, with no custom compiled encoder or renderer helper. Palette/string caches and asset loading are excluded from frame timing. Security settings remained enabled and unchanged. Tests ran on an ordinary active desktop; no CPU affinity, sustained clock measurement, thermal controls, or background-process isolation was applied.

An initial setup error sent UTF-8 half-block bytes to a console inheriting code page 437. Those terminal runs are preserved under `results/pre-utf8-fix/` and superseded. Current harnesses explicitly select and record code page 65001, then restore the original encoding. The figures below use corrected terminal runs; the separate headless measurements were unaffected.

A separate [console decoding probe](../results/terminal-utf8-check.json) confirmed that the same three raw bytes advanced the cursor three columns under code page 437 and one column under UTF-8, as intended for one half-block glyph. This verifies console decoding/cell advancement, while physical display inspection remains outstanding.

## Real Doom scene: measured combined loop

The input was the user's original Steam `DOOM.WAD`. The benchmark rotates through eight headings at the E1M1 player start, rendering walls, floors, ceilings, and sky. It excludes sprites, weapon, HUD, AI, collision, input, audio, and game-state simulation. It uses the external renderer's projection and shading, with no extra original-Doom aspect correction.

Each entry below is the range from two four-second runs. Both runs generate, encode, and write each update live with synchronized output enabled. **These are completed writes per second, not displayed FPS.**

| Logical image | Cached-string ANSI | Sixel with RLE | Sixel with bulk masks |
| --- | ---: | ---: | ---: |
| 147×92 | 75.4–76.4 | 33.8–34.1 | 64.9–65.1 |
| 320×200 | 21.9–22.3 | 11.2–11.3 | 19.0–19.2 |

Source: [doom-live.json](../results/doom-live.json). Ranges are observed repetitions, not confidence intervals or universal limits. Eight camera headings are a small scene sample, not smooth gameplay or a campaign benchmark.

Separately measured headless costs, after three warmups and over sixteen frames:

| Logical image | Median BSP render | ANSI encode | Sixel RLE encode | Sixel bulk encode |
| --- | ---: | ---: | ---: | ---: |
| 147×92 | 9.8 ms | 4.4 ms | 24.0 ms | 12.3 ms |
| 320×200 | 37.8 ms | 13.8 ms | 72.8 ms | 33.1 ms |

Source: [doom-scene.json](../results/doom-scene.json). Encoding includes UTF-8 conversion. These separate medians are not the component means of the later live runs and should not be summed to claim measured FPS. Runtime warmup and desktop variation can affect comparisons between separate runs.

The 320×200 offline image was inspected and shows recognizable textured E1M1 geometry. The PNG remains in ignored `local/`; it is not a screenshot of Terminal.

## What the synthetic experiments explain

The original per-character ANSI implementation spent 74.8 ms on a coherent 320×200 image. Cached strings plus one bulk concatenation reduced this to 6.6 ms with byte-for-byte equivalent output. The deliberately difficult entropy image decreased from 316.2 to 109.5 ms. This demonstrates a large implementation cost in PowerShell string construction. See [ANSI optimization](../results/ansi-optimization.json).

Sixel compresses these images much more tightly, but building the encoded representation can dominate. For the 256-color entropy pattern, replacing the PowerShell RLE scan with bulk ASCII conversion reduced median encoding from 610.4 to 294.9 ms while expanding the output from 341,354 to 2,456,543 bytes. On a coherent 16-color image the alternative was slower. The name `SixelFast` in scripts identifies this candidate, not a guarantee. See [Sixel optimization](../results/sixel-optimization.json).

The full 320×200/256-color synthetic loop produced these ranges over two five-second runs:

| Pattern | Cached-string ANSI | Sixel RLE | Sixel bulk |
| --- | ---: | ---: | ---: |
| Coherent tiles | 51.0–51.5 | 26.3–26.5 | 25.7–26.2 |
| High-frequency entropy | 9.3–9.5 | 1.7–1.7 | 3.4–3.4 |

Source: [terminal-live.json](../results/terminal-live.json). Units are completed writes/second. The entropy workload is deliberately difficult, not a prediction of a normal Doom frame.

## Terminal throughput and high refresh

Replay isolates output by keeping eight pre-encoded frames in memory and requesting 165 writes/second. In 32 synthetic cases, Sixel completed approximately 164.5–165.0 writes/second; coherent ANSI also reached the target. Difficult ANSI images of roughly 1.1 MB/frame completed about 72–78 writes/second. Sources: [synthetic replay](../results/terminal-replay.json), [Doom replay](../results/doom-replay.json).

All twelve real-scene replay cases, including ANSI at 320×200, completed 164.5–165.0 writes/second. This differed materially from the superseded ANSI runs and shows why explicitly matching the console code page mattered.

These finite runs show that writes can complete quickly. They cannot distinguish consumed, queued, coalesced, presented, and monitor-visible updates. Reaching the requested rate is not proof of maximum sustainable throughput. Synchronized output changed some write rates, but its effect on tearing, unique displayed frames, and latency remains unmeasured.

Windows Terminal's GPU renderer handles terminal presentation; it does not execute PowerShell's Doom arithmetic. Glyph antialiasing is separate from game-scene antialiasing. The installed renderer's synchronization path does not imply a universal 60 FPS cap; see [architecture and primary documentation](terminal-architecture.md).

**Unresolved:** PresentMon's independent presentation probe returned ETW access denied. No elevation, group membership, or security changes were made. Therefore this study has no verified displayed-FPS or input-latency result. Antialiasing modes and different physical Sixel sizes were not benchmarked against each other.

## Evidence-based direction

A low-resolution PowerShell experiment has support in these measurements. A full 320×200/60 FPS PowerShell Doom implementation is not demonstrated by this batch. Existing geometry rendering, game simulation, and terminal encoding need separate budgets.

The next useful batch is to profile and improve the pure PowerShell renderer/encoder on several real scenes, then add sprites and deterministic game ticks and measure the combined cost. ANSI is a useful baseline; Sixel merits further work because its bandwidth is low, but the encoder must earn that advantage. Any later C# or native hot-loop helper should be reported as a separate implementation category.

Keep a distinct presentation-validation task: visible correctness, unique displayed frames, scaling, and latency need direct evidence before claiming high-refresh play. Compare faithfully completed levels against a reference engine before calling an implementation a proper port.

The SSD's advertised sequential read speed is unlikely to decide a memory-resident frame loop; no disk throughput benchmark was run. These measurements suggest script and output costs deserve attention first. They do not establish a CPU-versus-memory hardware bottleneck from counters.
