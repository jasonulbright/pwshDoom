# Managed Doom source and reference audit

Reviewed 2026-09-27 against the [original C# Managed Doom repository](https://github.com/sinshu/managed-doom), its `README.md` reference list and test tree, the adopted PowerShell fork, and the study's current source and notes. This is an evidence-based inventory, not a claim that every listed resource has been fully audited or that the project matches every Doom port.

## Lineage and test oracle

The project does not implement the Doom game rules from scratch. Its game model began with Oleyska's PowerShell translation of Nobuaki Tanaka's C# [Managed Doom](https://github.com/sinshu/managed-doom), which its README describes as a manual translation of Linux Doom. `src/ManagedDoom/ORIGIN.md` records the exact PowerShell source pin, retained notices, and local changes. The original C# tree is useful for reviewing intended behavior and for selecting independent reference tests. It is not loaded by the playable PowerShell program, and this audit did not replace the PowerShell implementation with a C# runtime.

The original repository includes geometry and other unit tests plus compatibility fixtures for IWAD/PWAD demos, player movement and weapons, monsters, sector actions, map gimmicks, and multi-level transitions. Some map tests require a commercial IWAD or PWAD. On this machine, the reference project's `GeometryTest.PointToAngle` test passed under .NET 10. That result verifies the upstream C# test only; it is not a test of pwshDoom's PowerShell implementation. The PowerShell-side slope arithmetic received its own 50,006-case comparison against the C# unsigned-integer formula. Future port changes should use C# source/tests as a focused oracle where practical, while keeping production game and rendering algorithms in PowerShell.

## Original README references

| Reference | Project evidence and value | Disposition |

| [The Game Engine Black Book: DOOM](https://fabiensanglard.net/gebbdoom/index.html) by Fabien Sanglard | The local `docs/gebbdoom.pdf` copy was visually reviewed for architecture and rendering context. Particularly relevant pages: 168–170 (35 Hz ticks and 16.16 fixed point), 178 (WAD precedence), 186–197 (display/frame ordering), 202–218 (BSP and projection), 222–243 (visplanes, wall clips, masked sprites and weapon overlay), 246 and 252–258 (palette/audio), and 286–294 (demo timing and resolution/performance context). Pages 238–243 show the masked-sprite pipeline: projected sprite bounds, draw-segment silhouettes and screen-column clipping, back-to-front sprite drawing, masked midtextures, then the weapon overlay. A targeted comparison of pages 197, 208, 214, 240, and 242 with `FastRenderer.ps1` confirms the relevant plane-before-world-sprite ordering and per-column wall-silhouette clipping model. This explains why lower-sector Techpillar pixels may overlap a raised floor: classic Doom's visplanes do not later depth-occlude world sprites. The repository's two renderers produce near-identical Techpillar masks in the sampled screenshot regions (zero and three candidate-only pixels, respectively). This does not reproduce or resolve the separate exact-angle E1M1 pre-placed Gibs visibility report, nor establish independent original-binary parity. | Active design reference; no book pages, images, or source were copied into the repository. The PDF stays a local reading copy. The author's download page offers a pay-what-you-want PDF; that does not establish permission to redistribute it. |

## Recent PowerShell-fork updates

The PowerShell source was pinned at `e8440ae2f33f190318ebde4ef20ffec3bc804244`. A review of the fork's later September 2026 commits found a [September 22 numeric/default-value fix](https://github.com/oleyska/ManagedDoomPowershell/commit/e05c6f8511786d9813fc7aad7d03a34ecda87c5d) and a [September 23 performance commit](https://github.com/oleyska/ManagedDoomPowershell/commit/37b806c0dacc7afc1f4589a092fa9bfe0e35d83f). We adopted the narrow, demonstrably relevant `SlopeDiv` and player-angle corrections from the first commit, recorded in `src/ManagedDoom/ORIGIN.md`. We did not copy the fork's larger geometry rewrite or claim its author-reported renderer speedup for this separate host and renderer. The update review did not find a directly transferable fork fix for these visuals. Subsequent work in this repository reproduced and corrected a candidate-only BON1 wall-silhouette leak, and classified the raised-floor Techpillar overlap as expected classic plane/sprite behavior after same-state comparison of both repository renderers. The exact pre-placed `POL5` Gibs-through-wall sighting near the blue armor remains unreproduced at Jason's reported angle; it remains an open observation, not a confirmed product defect. See `docs/rendering-fidelity.md` for the pinned comparisons and their limits.

The PDF in `docs/` is a user-provided source copy, not a project asset. Keep it out of ordinary source commits and releases unless redistribution permission is separately established.
